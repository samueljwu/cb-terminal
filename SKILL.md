# CB Terminal Blueprint

## Product goal

Normalize convertible-bond prospectus terms and market-history rows into an auditable pricing workflow that surfaces fair value, parity, cheapness, and implied volatility for a coverage universe.

## Architecture

- `cb_terminal/domain`: dataclasses for contracts, assumptions, market snapshots/rows, diagnostics, pricing results, typed identities, and canonical JSON/dict serialization boundaries.
- `cb_terminal/io`: JSON contract loader, instrument identity registry loader, valuation-ready CSV market-history parser, raw CB quote-history CSV/XLSX parser, and daily equity/FX CSV/XLSX parser.
- `cb_terminal/pricing`: binomial pricing engine, implied-vol solver, `simple_crr` and preliminary `tf_split_tree` model modes, single-contract batch runner, universe batch runner, and static report writer.
- `cb_terminal/storage`: stdlib SQLite assumption snapshots, valuation runs/results, and dedicated raw CB price-history quote database.
- `cb_terminal/prospectus`: optional PDF/page-text extraction, conservative raw-prospectus inventory, automated ingest/review queue, duplicate controls, draft-contract creation, page-level source evidence, review reports, and coverage-universe helpers.
- `cb_terminal/web`: stdlib local HTML workbench, CB-universe dropdown UI, PM-safe unit-separated metric charts, guarded prospectus/contract review controls, and JSON API.
- `cb_terminal/cli`: command-line entry points.

## Data policy

- Prospectus-derived terms belong in normalized JSON under `data/contracts/`.
- Page-level term evidence belongs under `source_review.term_evidence`; evidence collection does not equal human approval.
- Automated extraction must not make up facts: scalar draft terms should be populated only when the raw PDF/page text has matching page/snippet evidence. Otherwise leave the field blank/`needs_review` and surface the evidence gap. Follow `CHECKLIST.md` for every prospectus extraction/OCR/LLM-assisted workflow.
- A single raw PDF can contain multiple CB series; auto-ingest must emit one `needs_review` draft and review-queue item per explicit series rather than silently using only the first maturity.
- Project isolation is mandatory: all cb-terminal procedural knowledge belongs in this project-local `SKILL.md`; do not add cb-terminal rules to global/cross-project skills such as `financial-data-pipelines`, and do not let cb-terminal workflows read/write sibling project folders unless the user explicitly requests a cross-project operation.
- Underlying equity tickers must infer Bloomberg suffix from nearby listing-venue evidence, not from whole-document country/legal language. Venue mapping: Taiwan/Taipei Exchange/TPEx/TWSE -> `TT`; Hong Kong/HKEX/SEHK/H-shares -> `HK`; Japan/Tokyo Stock Exchange/TSE -> `JP`; A-share/Shanghai/Shenzhen -> `CH`; USA/NYSE/Nasdaq -> `US`; Korea/KRX/KOSPI/KOSDAQ -> `KS`. Ambiguous bare stock-code hits without nearby venue evidence should remain `needs_review`.
- Same-maturity/same-size series must not be collapsed. Explicit Series A/B rows require separate draft contracts with series-specific conversion prices and series-specific ISIN/Common Code evidence. For Phison, Series A is `XS3364922461`, Series B is `XS3364929045`, and the underlying ticker is `8299 TT` from Taipei Exchange evidence.
- Prospectus extraction must search by contract-term semantics, not issuer-specific layouts. Prefer bounded evidence windows around term labels (`Issuer`, `Securities Offered`, `Issue Prices`, `Initial Conversion Prices`, `Exercise of Stock Acquisition Rights`, `ISIN/Common Code`, `General Information`) and series labels (`2029 Bonds`, `Series A Bonds`) over whole-document first-match extraction. For summary term tables like the WuXi AppTec pricing termsheet, parse the table row-by-row/label-by-label and extract every useful scalar term that has bounded evidence (currency/economic linkage, settlement currency, denomination, issue size, issue price, maturity redemption, conversion price, FX, identifiers, call/put/conversion windows). If a CB is explicitly Renminbi/CNH/CNY/RMB-linked or denominated, the risk-free/yield-curve currency should be the Renminbi leg rather than a USD settlement currency or HKD stock trading currency. For multi-series terms, extract the value paired with the same series label in the same table row/prose clause; do not reuse the first value for later series. Rules must stay broadly applicable across prospectuses and must not overfit issuer names, filenames, remembered answers, or a single checked-in example contract. Issuer names such as Issuer may appear in docs/tests as examples, but the runtime extraction layer must not branch on them.
- Extraction quality must be portable outside Hermes Agent. Runtime prospectus extraction must depend only on project code, raw PDF/page text, and declared optional dependencies such as PyMuPDF; no Hermes memories, global skills, sibling folders, or agent-only prompts may be required. The project-local `cb_terminal.prospectus.evidence.TERM_TARGETS` catalog is the durable list of terms the pipeline always searches for: ISIN/Common Code, issuer, underlying ticker, issue size, denomination, issue price, coupon, closing/issue date, maturity date, par/maturity redemption/premium, conversion price, conversion/exercise period, fixed FX, issuer calls, investor puts, dividend protection, and quote convention.
- The extraction pipeline has two layers: scalar normalization and targeted evidence discovery. Scalar normalization may populate JSON only when deterministic extraction found a specific evidence-backed value. Targeted evidence discovery should still surface candidate snippets for expected CB terms even if scalar normalization cannot safely decide the value yet; those candidates belong under `source_review.targeted_term_candidates` and in the review report, not in model inputs. If a PM manually adds a term in the GUI that was absent from the prospectus (for example `conversion.conversion_premium`), future extraction of the same raw PDF must preserve the existing contract JSON and must not overwrite or delete the manual field.
- Maturity redemption extraction must use bounded semantic windows around maturity-redemption labels, not punctuation-delimited clauses. Accept rows like `Redemption Price at Maturity ... 100.00% of principal amount`, including currency-equivalent wrappers such as `U.S. Dollar Equivalent of`, and principal/par-only redemption wording as 100.0 only when it is inside a bounded maturity-redemption context. Do not infer maturity redemption from issuer call, tax call, put, or cleanup-call principal-amount wording.
- ISIN extraction must support named letter series, year-labelled series, and single-series security-code headers. Search both directions for multi-series documents: `series label -> XS...` and `ISIN/Common Code heading -> series label -> XS...`. For single-series documents only, if no series-nearby match is found, use a bounded `Security Codes`/`ISIN` header block or a document-wide unique `XS...` identifier as the ISIN. If the raw PDF text has only a Common Code but no ISIN for a series, or if multiple unpaired ISINs remain, leave `canonical_id` blank and keep `PENDING_ISIN`.
- Underlying ticker extraction should accept jurisdiction-specific labels when backed by nearby venue evidence. Japan examples may use `Securities Identification Code for the Shares ... is 5016`; with nearby `Securities Identification Code Committee of Japan` or `Tokyo Stock Exchange` evidence this maps to `5016 JP`. Do not substitute stale memory or filename guesses for raw-PDF evidence.
- JX Advanced Metals final OC regression facts from raw PDF text: 2029 Bonds `XS3353961033`, issue price `110.75%`, maturity `2029-06-04`, conversion end `2029-05-21`; 2031 Bonds `XS3353961116`, issue price `111.50%`, maturity `2031-06-03`, conversion end `2031-05-20`; both use ticker `5016 JP` and initial conversion price `JPY 4,860`.
- Curated page-text fixtures for deterministic evidence matching belong under `data/prospectus_text/` and must be replaced by direct PDF/OCR extraction before production approval.
- PDF extraction must fail closed: if PyMuPDF is unavailable or installed but cannot open a malformed/scanned PDF, return an auditable `ExtractionResult` with warnings rather than raising through inventory/auto-ingest workflows. The extraction summary must include explicit runtime preflight (`text_backend_available`, optional OCR availability), a failure class (`backend_missing`, `backend_failed`, `needs_ocr`, `partial_low_text`, `text_extracted`), and per-page text counts/density so scanned PDFs are separated from missing parser templates. Install text-layer PDF support with the optional `prospectus` extra (`uv venv .venv && uv pip install --python .venv/bin/python -e '.[prospectus]'`).
- Raw PDFs and private exports belong under ignored `data/raw/` or outside the repo.
- `data/coverage/prospectus_inventory.json` may list raw PDFs and extraction status, but prospectus-only records must not enter pricing until a normalized contract and market history exist.
- `data/coverage/review_queue.json` is the automated intake queue. Only `contract_available_needs_review` items have draft contracts; `needs_extraction_backend`, `needs_ocr`, and `needs_manual_template` are blocked from pricing.
- Duplicate contracts are prevented by ISIN when present, otherwise issuer + underlying ticker + maturity date. Existing contract paths are never overwritten by auto-ingest.
- Raw prospectus PDFs may be deleted or archived only after the linked contract is explicitly `status: reviewed`, the stored SHA-256 matches the file, the raw path remains under `data/raw/prospectuses`, and the API caller supplies typed confirmation matching the contract id or source filename.
- Market history is database-backed with CSV audit/export artifacts and separate from contract terms.
- Domain objects that cross API/storage/audit boundaries must round-trip through `DomainSerializable.to_dict()` / `.from_dict()` or the shared `DomainJSONEncoder` rather than ad-hoc `json.dump` handling. Dates are ISO strings, `FXConvention` and other enums are their stable values, and nested dataclasses must remain plain JSON-compatible payloads. This OpenLIFU-inspired boundary keeps pricing results, assumptions, market rows, diagnostics, and contracts replayable across CLI, web, SQLite metadata, and JSON artifacts.
- `data/cb_terminal.sqlite` is the canonical metadata/state catalog for instruments, contracts, source files, import batches, coverage membership, FX canonicals, valuation market series/rows, assumption sets, and valuation runs/results. JSON indexes (`data/coverage/*.json`) and generated CSVs are compatibility/audit artifacts that should be synced into this catalog, not new competing sources of truth.
- `data/coverage/instruments.json` is the portfolio identity registry: use a typed identity object with `instrument_key`, `instrument_type`, `primary_id_scheme`, and `primary_id` at API/database boundaries. For finalized CBs, `contract_id` must be `[ISIN]_contract` (for example `XS3236970433_contract`) and `display_id` must be `[short name] [coupon] [two-digit maturity year]` (for example `Issuer 0 31`). Do not introduce parallel CB join IDs such as `canonical_id`, `cb_instrument_id`, issuer-derived slugs, or deal-name IDs; source labels belong only in aliases/provenance, not join keys.
- Draft/launch-only CBs without an ISIN must be marked `canonical_id_type: PENDING_ISIN` and kept indicative/needs-review until the final identifier is known.
- Raw CB quote exports and daily equity/FX exports belong under `data/price_history/raw/`; GUI Data Upload imports them into the generated `data/price_history/price_history.sqlite` database instead of merely parsing row counts or mixing them with valuation-ready market-history CSVs. Raw CB quotes are observed provenance only; valuation-ready market history is the generated/validated pricing input after raw quotes, stock history, and canonical FX are joined. Data Upload should stay PM-simple: one prospectus PDF input and one market-data input; both inputs may accept multiple selected files in one upload action. The market-data upload must auto-classify each supported CB quote history, equity history, FX history, valuation-ready history, or explicit mixed CSV file, then import every recognized stream without asking the user to choose a type. PM-facing coverage state should answer, per CB: terms extracted, CB quote history date range, equity history date range, global FX history date range by currency pair, and resulting valuation-history date range. The Data Sources tab must expose `/api/market-generation-readiness` diagnostics for the active contract: expected CB/equity/FX identifiers from contract terms, imported SQLite date ranges/source files, explicit missing inputs, and no-overlap status before and after `Generate valuation CSV`.
- The raw price-history database stores observed bid/ask/mid quote provenance and market-data points; `cb_terminal.cli.build_market_history` joins them into valuation-ready rows. FX market-data uploads maintain one canonical source per currency pair in `data/coverage/fx_sources.json`; preserve an existing canonical pair source unless the caller explicitly confirms overwrite.
- The default GUI/universe market history for any covered CB should be a generated multi-date valuation CSV, not one-row `anchor` fixtures under `tests/fixtures/`; checked-in issuer files are examples only.
- PM/trader assumptions are stored as append-only SQLite snapshots under `assumption_sets`; GUI what-if preview does not become durable until explicitly saved.
- PM-facing valuation charts must be grouped by y-axis unit: price stack (market/model/parity/floor), cheap/rich, implied volatility, underlying stock, FX, and assumption rates. Do not reintroduce raw mixed-axis overlays for unlike metrics. Browser charts should support lightweight time-window zoom/pan without adding Chart.js or a heavy frontend dependency; normal wheel scrolling over charts should keep scrolling the page, with chart wheel-zoom gated behind an explicit modifier such as Ctrl/⌘/Alt. PM View charts are intentionally a bit shorter than diagnostic charts: use PM-specific CSS classes/viewBox heights when shrinking the PM View so valuation/audit/raw-quote tabs can keep their established sizing. Instrument navigation is global and keyboard-first: the top command bar accepts ISINs or deterministic display IDs, spans the page as the primary command surface, supports keyboard autocomplete suggestions, and defaults to an empty/no-CB-loaded state instead of auto-selecting demo data. Actual issuer names should display when they come from the loaded CB data; avoid hardcoded issuer examples or special cases. Detailed editable pricing inputs belong in an Assumptions tab immediately before PM View, and PM View must keep a compact active-assumptions strip plus an Edit assumptions jump so PMs can see what drives the valuation without leaving the decision view.
- GUI assumption entry uses PM display units: credit spread in bps, volatility/borrow/dividend/yield-curve/manual RF in percent. Convert display values to decimals at the API boundary with an explicit `input_units: display` marker while keeping decimal API/backtest compatibility.
- GUI prospectus review must let the PM run conservative pending-PDF extraction/intake, then rename or delete only raw, unlinked pending prospectus PDFs under `data/raw/prospectuses`; linked raw prospectus cleanup remains guarded by reviewed status + checksum + typed confirmation through the contract-level action.
- GUI contract review may edit only an explicit allowlist of scalar contract terms under `data/contracts`; arbitrary JSON fields, source paths, evidence, and `status=reviewed` approval must not be writable through the general term editor. Material edits reset review state to needs-review, create a backup, and keep review-queue status synchronized.
- GUI term approval is a separate explicit action from saving edits or deleting/archiving raw PDFs. Approval may mark a contract `reviewed` only through the dedicated approval flow, should write source-review audit fields, must block missing approval-critical page-level evidence unless an explicit reviewed exception flow exists, and must keep `data/coverage/review_queue.json` aligned with the contract JSON status. Audit-only evidence gaps such as instrument description, closing date, or unnormalized conversion period dates should stay visible in the evidence matrix/review report but should not block pricing approval when the valuation engine does not consume them or the raw termsheet states them only relatively (for example, "after Closing Date").
- GUI prospectus review should show page-level evidence beside each editable term row (page/match/confidence/snippet), not only in a separate evidence dump, so the PM can check term value and source text in one pass. Term-row evidence badges must use the same usable page-citation rule as approval (`page >= 1`, non-empty snippet, non-empty match type), not just key/list presence, so the UI cannot show malformed evidence as present before approval rejects it.
- Prospectus Intake raw-PDF inbox must not depend solely on `data/coverage/review_queue.json`: raw PDFs under `data/raw/prospectuses/` are the shared discovery source, and `/api/review-queue` / `/api/sources` should reconcile missing pending rows into both `review_queue.json` and `prospectus_inventory.json` so Data Sources and Prospectus Intake cannot drift after direct file copies or index resets. Rename/delete from Prospectus Intake must update both indexes and refresh Data Sources; Data Sources remove should treat an already-missing pending raw PDF as an idempotent stale-index cleanup rather than a hard error. Reconciliation must also prune stale pending inbox rows once the same raw PDF is linked to an extracted contract by path or SHA-256, otherwise the GUI shows a raw file as delete-able in Prospectus Intake while the lifecycle guard correctly blocks it as contract-linked. Pending raw actions must be able to resolve legacy filename-only queue rows by falling back to `data/raw/prospectuses/<source_filename>`.
- GUI Data Sources is the inventory/library view for uploaded raw files and pre-processed canonical sources. Keep Data Upload upload-only, then expose a top-level `Data Sources` tab listing project-relative raw prospectus PDFs, raw quote/market files, generated valuation-history CSVs, and contract JSON files. Prospectus uploads belong only in Data Upload; Prospectus Intake manages raw PDF selection/extraction/review and should not duplicate upload controls. Selection controls should be consistent across Data Sources and Prospectus Intake raw-file tables: explicit checkbox controls, row-click toggle selection, Shift-click range selection, a separate active row for detail/singular actions, and shared `selected-row` styling. Dashboard tables should be column-sortable from their headers, including dynamically rendered tables, with numeric/date-aware sorting and non-data selection columns left unsorted. The table must show PM-facing linkage/status, never absolute paths, and compute action permissions in the backend. Rename/remove actions are allowed only through guarded source APIs; linked raw prospectuses remain blocked unless using the reviewed contract-level prospectus action, and contract edits should route to Terms / Evidence / Actions rather than arbitrary JSON editing. Raw CB quote, stock, and FX history uploads are provenance/source-library inputs: auto-classify and import them by identifier, show matched CB coverage, but do not persist them to the selected CB or expose manual `raw_price_history_path` linking. FX history is global currency-pair data, not CB-linked. Only generated valuation-ready market-history CSVs may be contract-scoped via `data/coverage/universe.json` (`market_history_path`). Data Sources should expose `Refresh matches` and `Generate valuation CSV` rather than `Link to selected CB`; generation joins CB quote + stock + FX histories and then links the resulting CSV to the selected contract. The generate action must resolve an explicit loaded/opened contract path, never a blank hidden-select value that falls through to the first option, and must distinguish missing inputs from no overlapping dates. The Data Sources linked column should display `instrument_display_name`/short CB labels such as `Issuer 0 31`, not legal issuer names such as `Issuer Corporation`. If a selected CB is visible through `review_queue.json` but absent from `universe.json`, generated valuation-history linking should promote a minimal universe row for that exact contract before writing the link. After a generated Data Sources link or generated valuation CSV, reload `/api/universe`, preserve the selected contract, copy refreshed `market_history_path` into the valuation form, and re-run pricing only when a valuation-ready market-history CSV is available; otherwise clear stale PM charts/KPIs. Raw quote-history matching should auto-match by exact ISIN/instrument-id in the source file; mismatched selected CB vs generated CSV CB identity must still be rejected.
- Generated valuation-history links must validate the selected contract before persisting: priced cross-currency rows require explicit `market_fx_rate` and `fx_convention` (`STOCK_PER_CB` or `CB_PER_STOCK`) so missing FX is reported clearly and the GUI cannot mark a CB valuation-ready while silently defaulting to 1.0. FX matching must accept both direct Bloomberg pairs such as `USDTWD Curncy` (`STOCK_PER_CB` for USD/TWD) and inverse pairs such as `TWDUSD Curncy` (`CB_PER_STOCK`) instead of reporting `missing: fx_history` when a usable inverse source is uploaded. For CNH/CNY-linked but USD-settled CBs with USD quote history and HKD stock history, the valuation-history generator must use the settlement/quote currency for market FX requirements (`USD/HKD`, e.g. `USDHKD Curncy`) while preserving the Renminbi leg as the economic/yield-curve currency. `/api/universe` exposes a single `canonical_source` per CB carrying contract terms and valuation market history from the contract-scoped coverage row; `/api/universe`, `/api/sources`, and `/api/source-inventory` also expose canonical SQLite store metadata (`canonical_store`, `canonical_record_id`, `canonical_source_id`) while retaining project-relative paths for UI compatibility. GUI pricing defaults should resolve market paths from that canonical row so features do not drift. Raw market-data source rows in Data Sources must be enriched from the SQLite import tables: CB quote files can match one CB, multiple CBs, or unknown/not-yet-in-database CB IDs, and their status should say `matched_market_source`, `matched_multiple_cbs`, `partially_matched_market_source`, or `unmatched_market_source` rather than collapsing to `uploaded_unlinked`; FX-only files should be `global_fx_source`.
- Prospectus Intake raw-PDF actions should use compact command groups with short visual labels and full `aria-label`/`title` text: e.g. INTAKE group `Extract selected`, `Extract all`, `Refresh`; FILE group `Rename`, `Delete`. Preserve existing button ids/event handlers and keep destructive actions visually distinct without leaving the black terminal aesthetic. Reuse modular UI helpers for repeated workflow elements such as determinate progress bars instead of adding one-off DOM-manipulation code; Data Sources CB-link progress and Prospectus Intake extraction progress should share the same progress component helper so labels, ARIA state, and bar behavior stay consistent.
- PM-facing CB labels must be deterministic short display names separate from legal/raw names: `instrument_display_name`/`instrument_short_name` are short labels like `JX 0 31`, `Issuer 0 31`, or `Hongqiao 0 30`; `instrument_legal_name`/`issuer_legal_name` preserve the full legal issuer; `instrument_raw_display_name` preserves the extracted/raw name for provenance.
- The web `/api/universe` payload must merge valuation-ready `data/coverage/universe.json` instruments with extracted draft contracts in `data/coverage/review_queue.json`. A newly extracted CB must appear immediately in the PM view and single-CB dropdown using `instrument_display_name`, even if it is not yet priceable because market history is missing.
- Keep the default XS3236970433 issuer-neutral fixture coherent across `data/contracts`, `data/coverage/instruments.json`, `data/coverage/universe.json`, raw quote XLSX, generated valuation CSV, and `data/cb_terminal.sqlite`. Valuation CSV generation regressions should be tested against Bloomberg-style equity/FX XLSX layouts like the user-supplied `equity-price-history.xlsx` / `FX-price-history.xlsx`: import raw CB quotes, stock history, and direct/inverse FX history into the price-history store, then verify `Generate valuation CSV` writes/validates/links a multi-date valuation CSV. Auto-detection should not emit scary missing-default-contract warnings while merely checking whether an arbitrary raw CSV is already valuation-ready.
- Universe reports under `data/reports/` are replayable artifacts generated from `data/coverage/universe.json`, contract JSON, market CSVs, and explicit assumptions.
- Assumptions must be explicit and replayable in outputs.

## Validation

Run:

```bash
.venv/bin/python -m unittest discover -s tests
.venv/bin/python -m compileall -q cb_terminal tests
.venv/bin/python - <<'PY'
import fitz
print('PyMuPDF ready', getattr(fitz, '__version__', 'unknown'))
PY
```

For UI/API work, also smoke-test `python3 -m cb_terminal.cli.serve`, `/api/universe`, and `/api/batch-price`; verify the default payload has more than one valuation date.
For prospectus-extraction changes, run the rotated holdout harness with the project venv and prospectus extra installed: `.venv/bin/python scripts/prospectus_leave_one_out.py --min-core-score 1.0 --min-core-evidence-score 1.0 --min-optional-score 0.8 --min-optional-evidence-score 0.8`. This is a development validation/refinement harness only: it rotates every raw PDF under `data/raw/prospectuses/` as holdout and reports training/holdout core and optional term coverage, but it must not become a runtime extraction feature or product workflow.
For portfolio work, smoke-test `python3 -m cb_terminal.cli.prospectus_inventory`, `python3 -m cb_terminal.cli.prospectus_auto_ingest --project-root .`, import raw CB quote history and equity/FX into a temporary DB, build a generated valuation-ready market-history CSV, and run `python3 -m cb_terminal.cli.price_universe` against checked-in examples.
